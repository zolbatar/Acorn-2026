# Tokenized BASIC compatibility matrix

## Purpose

Keep saved-file decoding, token interpretation, and execution coverage separate. The decoder preserves token bytes and normalizes observed record layouts into the same line-oriented program model. The compatibility runner then selects language behavior; a successful load does not imply that the program can run.

The user requirement is to load tokenized programs from every earlier BBC BASIC release. The reference manual identifies BASIC I, II, III, IV, V 1.04, V 1.05, and VI 1.05. Current fixtures establish a useful starting point without claiming complete coverage.

## Release inventory

| Release | Target and distinguishing evidence | Fixture coverage |
| --- | --- | --- |
| BASIC I | Early BBC Micro Model A/B; original interpreter. | No release-identified saved file yet. |
| BASIC II | BBC Model A/B; adds `OPENUP` and `OSCLI`. | No release-identified saved file yet. TDU-01 is retained as an optional graphics-development input and shared-layout evidence; its ROM version is unknown, so it is not BASIC II coverage. |
| BASIC III | BBC Model B+; largely BASIC II plus the US spelling `COLOR`. | No release-identified saved file yet. |
| BASIC IV | BBC Master series and 65C12 second processors. | TETRIZ 1.5 is Master-targeted BASIC IV-class evidence; exact ROM revision is unknown, and its use of BASIC IV-only tokens is not established. It is not a required whole-program execution target. |
| BASIC V 1.04 | ARM / RISC OS. | No independent saved binary yet. |
| BASIC V 1.05 | ARM / RISC OS; later interpreter release. | No independently saved binary yet. ClockSP5's generated token file exercises an ARM token profile but does not verify this interpreter release; `5.08` is the program version. |
| BASIC VI 1.05 | ARM / RISC OS; IEEE 8-byte real representation. | No independent saved binary yet. |

The release distinctions above follow the [BBC BASIC history appendix](https://www.riscos.com/support/developers/bbcbasic/appendices/basichistory.html). It identifies BASIC IV as the Master / 65C12 release and distinguishes V 1.04, V 1.05, and VI 1.05.

## Observed saved-program layouts

The current corpus contains two byte-level line-boundary layouts:

| Layout | Boundary bytes | Evidence |
| --- | --- | --- |
| Shared boundary carriage return | A `0D` at the next-record boundary terminates the prior line and starts the next record. | `tdu-01-test.bbc` from public-domain TDU-01 and `tetriz-master-basic4.bbc` from public-domain BBC-134. |
| Separate line carriage return | A line-ending `0D` is inside the record length, followed by another `0D` marking the next record. | The project-generated ARM BASIC V ClockSP5 and echo fixtures. |

The shared decoder auto-detects these layouts per program, rejects a file that mixes them, preserves each line's token bytes, and scans line references with layout-appropriate token rules. The inferred layout is not an exact interpreter-version identifier.

The matrix deliberately labels exact ROM revisions as unknown where the disk provenance does not identify them. The shared-boundary profile now includes a conservative common graphics statement subset alongside leading-`REM`, literal-string `PRINT`, and `END`; it is not an inferred BASIC I/II/III/IV release. ClockSP5 exercises the ARM token profile, but its binary was generated from text and therefore does not verify a binary saved by a real BASIC V interpreter.

## External ARM BASIC V source candidates

These sources were selected as candidate engineering inputs for hosted source compatibility and, where suitable, JIT workload discovery. They are not yet release-acceptance fixtures. A source file, a converter-produced token file, and a save made by a named BASIC V interpreter are distinct evidence and must remain labelled separately.

| Source | Evidence and intended use | Limits |
| --- | --- | --- |
| [MAL BBC BASIC V implementation](https://github.com/kanaka/mal/tree/master/impls/bbc-basic) | Eleven staged files, from `step0_repl` through `stepA_mal`; the project says this implementation runs on ARM BBC BASIC V under RISC OS 3 or later. Use the stages as portable source-semantic coverage. The repository is MPL-2.0. | Source compatibility does not establish a ROM-saved file or exact V release. The self-hosted Lisp interpreter is a dynamic workload, not by itself a clean numerical JIT benchmark. |
| [WimpLib](https://github.com/steve-fryatt/wimplib) | RISC OS and Wimp routines written in BASIC. Its source is plain text and can be built as tokenised BBC BASIC or BASICTxt; the repository is EUPL-1.2. Prioritise it once the corresponding Wimp and SWI services are available, for library and OS-facing compatibility. | Do not require whole-library execution before those services exist. Its OS-facing routines should not be assumed to be useful compute benchmarks. |
| [Dave Gardner's Archimedes archive](https://github.com/davegardnerisme/riscos) | An author-described archive of BASIC programs written for Archimedes between about 1992 and 1996. The `Notify` source is detokenised for browsing, and its program package is available for inspection. Useful as a period-source challenge, including `SYS` and byte/word indirection. | The exact BASIC ROM release is unidentified and the repository has no explicit reuse license. Keep it external until provenance and terms are clarified; do not count it as a version-specific saved-file fixture. |

[Steve Fryatt's Tokenize](https://github.com/steve-fryatt/tokenize) can convert text into ARM BASIC V-style tokenised files and process `LIBRARY` statements. Its README says it is not a full BASIC syntax checker. Treat its output as converter-generated format evidence, not as a save from a specific BASIC V ROM.

Preserve each source repository's license and attribution when creating local fixtures, and check license compatibility before copying sources into this repository. Select JIT workloads separately by profiling eligible procedures; Wimp activity and dynamic-language work can validate fallback and runtime boundaries without serving as numeric speed claims.

## Retained Agon demo

The only Agon demo included in the repository is [`demo-volume/AgonTREE.bbc`](../demo-volume/AgonTREE.bbc), with metadata in its `.acornmeta` sidecar. The host filename is `AgonTREE.bbc`; HostFS exposes it as guest file `TREE` at the root of the default `DemoDisk` volume. Load it with `BASICLOAD HostFS::DemoDisk.$.TREE` and run it with `BASICRUN`. Its leading `REM @BASIC64 MODE=CLASSIC TARGET=AGON` line records its intended language mode and target. The listing credits Andy Fandango (@Pixel_Fandango) and includes its source video link.

The demo requests Agon mode 20 (512 × 384, 64 colours), which differs from RISC OS mode 20 (640 × 512, 16 colours). `TARGET=AGON` selects the hosted Agon graphics mode table, but the hosted runtime does not implement the Agon VDP protocol, firmware, or GPIO services. The fixture is a single target-specific demo, not evidence of broad Agon compatibility or a BASIC V ROM save. Integer ARM-style `@%` fixed/exponent controls are supported, but complete field-width and formatting rules remain unsupported; see the [BBC BASIC reference](https://www.riscos.com/support/developers/bbcbasic/bbcref.html).

The hosted graphics path is an additional source-compatibility slice, not a new release-specific execution profile. `OS_WriteC` feeds the VDU stream parser, while BASIC `LINE`/`MOVE`/`DRAW`/`PLOT` statements use the hosted `OS_Plot` service. The standard numbered RISC OS modes use their PRM Table B dimensions and retain plot primitives; text-only modes suppress pixel plotting, and mode 7 renders Teletext cells and basic control-code attributes. The selected extended 32-bit mode uses a shared RGBA raster surface so per-pixel programs do not accumulate plot history. This does not execute machine-code `CALL` statements or claim full VDU, palette, ColourTrans, or Teletext coverage. TDU-01 guides this work without becoming a release or whole-program compatibility requirement.

[`examples/mandelbrot/mandelbrot.bas`](../examples/mandelbrot/mandelbrot.bas) is copied from the RISC OS 5.22 listing in [“Mandelbrot plotters for BBC BASIC”](https://barrowbiker.wordpress.com/2016/12/25/mandelbrot-plotters-for-bbc-basic/) (Barrowbiker's Blog, December 25, 2016). The post invites readers to use the code but does not state a formal license. The generated [`mandelbrot.bbc`](../examples/mandelbrot/mandelbrot.bbc) assigns sequential line numbers and encodes the source with the project token encoder; it is not a tokenized BASIC `SAVE` and does not establish general BASIC V/VI compatibility. The hosted run path supports the syntax and operations this listing uses in its selected C16M branch: parameterized `PROC`/`FN`, string and word indirection, string functions and `MID$` assignment, `<<`, multiline `IF` blocks, extended 32-bit `MODE`, `INKEY(0)`, and the two invoked `ColourTrans` SWIs. The full 1680 × 1050, 8192-iteration workload can take a while under interpretation. See the fixture README for regeneration and run instructions.

[`examples/mandelbrot/reduced.bas`](../examples/mandelbrot/reduced.bas) and its generated `.bbc` counterpart are project-authored development fixtures, not release evidence. The reduced program uses standard RISC OS MODE 12 (640 × 256, 16 colours) and at most 48 iterations per pixel. It runs through the ARM BASIC V token profile using the hosted `MODE`, `GCOL`, and `PLOT` path; snapshots during `BASICRUN` are limited to about 60 updates per second, followed by a final snapshot. The fixture README documents regeneration and run steps.

## Test harness

Run `cargo test`. The `tokenized_compatibility` integration test walks the checked-in corpus and checks each program's detected layout, line count, line-reference count, and unresolved-reference count. Decoder unit tests also cover malformed records, quoted/DATA/REM text, classic `DELETE` line references, ClockSP5's exact reference destinations, and the authentic BBC Micro and Master fixtures' line boundaries. The shared-boundary core fixture can be run with `BASICLOAD examples/tokenized-compat/classic-core-smoke.bbc` followed by `BASICRUN`.

When adding a fixture, record its source, claimed interpreter/version, license or redistribution terms, layout, line/reference counts, and whether its bytes came from an actual BASIC `SAVE` or a project converter. Do not promote an unpinned fixture to a specific release row based only on its syntax.
